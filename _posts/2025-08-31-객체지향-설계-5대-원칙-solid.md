## 1. SRP (Single Responsibility Principle)

> 단일 책임 원칙: 클래스는 **하나의 책임**만 가져야 한다.

```text
[잘못된 설계]
UserService ──> 회원가입 + 이메일 발송 + 결제 처리  ❌

[✅ 올바른 설계]
UserService ──> 회원가입만 책임
MailService ──> 이메일 발송
PaymentService ──> 결제 처리
```

**예시**

* Controller : 요청 받기
* Service : 비즈니스 로직
* Repository : DB 접근

## 2. OCP (Open/Closed Principle)

> 개방-폐쇄 원칙: **확장에는 열려** 있고, **변경에는 닫혀** 있어야 한다.

```text
[❌ OCP 위반]
OrderService 가 KakaoPay 클래스에 직접 의존

[✅ OCP 적용]
OrderService -> Payment 인터페이스에만 의존
└── KakaoPay / NaverPay / TossPay 등 교체 가능
```

**예시**

```java
public interface Payment { void pay(); }
public class KakaoPay implements Payment { ... }
public class NaverPay implements Payment { ... }

@Service
public class OrderService {
    private final Payment payment;
    public OrderService(Payment payment) { this.payment = payment; }
}
```

## 3. LSP (Liskov Substitution Principle)

> 리스코프 치환 원칙: 부모 타입을 사용하는 곳에서 자식 클래스로 **교체해도 문제 없어야** 한다.

* `BookService`는 **BookRepository 인터페이스만 바라본다**.
* DB 기술을 바꾸더라도(JPA → Mongo) `BookService`는 수정할 필요가 없다.
* 구현체만 교체되면 정상적으로 동작!

```java
// 부모 타입 (인터페이스)
public interface BookRepository extends CrudRepository<Book, Long> {
    
    // 공통 메서드 (CrudRepository에서 기본 제공)
    List<Book> findByTitleContaining(String keyword);
}
```

```java
@Service
public class BookService {
    private final BookRepository bookRepository;

    public BookService(BookRepository bookRepository) {
        this.bookRepository = bookRepository;
    }

    public Book save(Book book) {
        return bookRepository.save(book);
    }

    public List<Book> search(String keyword) {
        return bookRepository.findByTitleContaining(keyword);
    }
}
```

* 만약 프로젝트에서 Spring Data JPA만 의존성에 포함시 → JpaBookRepository가 자동 주입
* MongoDB만 사용한다면 → MongoBookRepository가 자동 주입
* 두 개 다 존재한다면 → `@Primary,` `@Qualifier` 등을 이용해 어떤 걸 주입할지 선택

```java
// JPA 환경에서의 구현체
public interface JpaBookRepository extends BookRepository, JpaRepository<Book, Long> {
    // JPA 특화 기능도 추가 가능
}

// MongoDB 환경에서의 구현체
public interface MongoBookRepository extends BookRepository, MongoRepository<Book, String> {
    // Mongo 특화 기능도 추가 가능
}
```

## 4. ISP (Interface Segregation Principle)

> 인터페이스 분리 원칙: 클라이언트가 **쓰지 않는 메서드에 의존하지 않게** 분리한다.

```text
[❌ 잘못된 예시]
interface BigInterface {
   save();
   delete();
   paging();
   sort();
   caching();
}

[✅ 올바른 예시]
CrudRepository<T, ID> { save(), delete() }
PagingRepository<T>   { paging() }
```

* CrudRepository + PagingAndSortingRepository → 필요한 기능만 선택적으로 상속

## 5. DIP (Dependency Inversion Principle)

> 의존 역전 원칙: 구현 클래스가 아니라 **추상화(인터페이스)에 의존**하라.

```text
[❌ 잘못된 설계]
OrderService ──> KakaoPay (구체 클래스 직접 의존)

[✅ DIP 적용]
OrderService ──> Payment (인터페이스)
                     ├─ KakaoPay
                     └─ NaverPay
```

**예시 (DI 주입)**

```java
@Service
public class OrderService {
    private final Payment payment;

    // IoC 컨테이너가 구현체 주입
    public OrderService(Payment payment) {
        this.payment = payment;
    }
}
```

## 간단요약!

1. **SRP** : 하나의 책임만 (Controller, Service, Repository 분리)
2. **OCP** : 확장엔 열려, 변경엔 닫혀 (DI로 교체 가능)
3. **LSP** : 부모타입 = 자식타입 (호환성 보장)
4. **ISP** : 인터페이스는 작게 분리 (필요한 기능만)
5. **DIP** : 추상화에 의존 (스프링 DI의 핵심)
