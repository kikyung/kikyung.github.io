## AI 시대에 다시 읽은 이유

데이비드 토머스와 앤드류 헌트의 《실용주의 프로그래머》. 4년 전쯤 대충 훑어본 것 같은데 지금 시대에 다시 필요해 보여서 읽었습니다.

요즘은 코드를 직접 작성하는 시간보다, AI가 만든 코드를 읽고 고치고 판단하는 시간이 더 중요해진 것 같습니다. 그러면 어떤 언어나 도구를 익히느냐보다 **어떤 기준으로 코드를 바라볼지**가 더 중요해 보이고요.  
이 책은 그 기준을 다시 잡아주는 느낌이었습니다.

---

## 핵심 원칙들

### 바꾸기 쉬운 코드가 좋은 코드다

> ETC — Easier To Change

좋은 설계란 바꾸기 쉬운 설계라는 뜻입니다.

- 결합도 낮추기, 책임 나누기, 중복 줄이기 — 이런 원칙들도 결국 나중에 고치기 편하려고 하는 것
- AI가 돌아가는 코드를 금방 만들어줘도, 그게 다음 요구사항을 막아버리면 별로임
- "이거 나중에 바꾸기 쉬운가?" 이 질문 하나가 생각보다 자주 쓰이더라고요

### DRY — 복붙 금지가 아니다

DRY(Don't Repeat Yourself)를 단순히 무분별하게 복사붙여넣기 하지 말라는 뜻으로 생각하고 있었는데 좀 더 명확해 진것 같습니다.

> 하나의 지식이나 규칙이 여러 곳에 흩어지지 않게 하라

- 코드가 달라도 같은 비즈니스 규칙을 반복하면 → 중복
- 코드가 같아도 의도가 다르면 → 굳이 합칠 필요 없음

이 구분이 실용적이라 느꼈습니다.

### DBC와 TDD — 서로 다른 층위의 검증

> **D**esign **B**y **C**ontract: 함수가 "이런 조건이면 이런 결과를 보장한다"는 계약을 명시하는 방식

선조건·후조건·불변식을 코드에 표현해서 문제가 생기면 즉시 드러나게 합니다.

책에서는 DBC와 TDD를 보완 관계로 설명하고 있습니다.

- **TDD** — 밖에서 볼 때 이렇게 동작해야 한다를 테스트로 먼저 정의
- **DBC** — 안에서 이 조건이면 이 결과를 보장한다를 코드에 명시

테스트는 특정 경로가 제대로 동작하는지 확인하지만 모든 경우를 다 검증하기는 어렵습니다. DBC는 런타임에 계약 위반을 감지해서 테스트가 놓친 부분을 잡아줄 수 있고요. 결국 경쟁이 아니라 서로 다른 층위에서 코드의 올바름을 지키는 장치로 이해됐습니다.

AI로 작업할 때 이 관점을 염두에 두고 검토 장치를 설계하는 기준으로 삼으면 좋겠습니다.

## 불확실한 프로젝트에 접근하기

### 예광탄 vs 프로토타입

둘 다 빠르게 만들어본다는 점은 같지만 목적이 다릅니다.

| 구분 | 예광탄 | 프로토타입 |
|------|--------|------------|
| 목적 | 전체 시스템을 관통하는 얇은 구조로 방향 확인 | 특정 위험이나 기술적 가능성 확인 |
| 코드 재사용 | 계속 발전시킴 | 폐기 전제 |

최근 하나투어 연동 프로젝트에서 프로토타입 방식을 적용해봤습니다.  
복잡한 API 구조를 참여자들이 빠르게 파악할 수 있도록 AI를 활용해 단계별로 접근 가능한 전체 UI를 먼저 만들었는데요.  
실제 데이터가 어떻게 흐르는지 눈으로 확인할 수 있게 되니, 동료들과 전체 구조를 이해하는 데 큰 도움이 됐습니다.

다만 AI 덕분에 예전보다 훨씬 빠르게 만들어볼 수 있게 된 만큼, 검토 없이 다음 단계로 넘어가기도 쉬워졌습니다.  
AI가 만든 프로토타입이 그럴듯하게 돌아간다고 제품 코드로 써도 되는 건 아니니까요. 어디까지 확인용 코드였는지 경계를 분명히 해야 합니다.

### 지식 포트폴리오

지식을 금융 포트폴리오처럼 관리하라는 조언도 인상적이었습니다.

- 매일 조금씩 투자
- 한 가지 기술에만 몰리지 않도록 분산
- 유행하는 정보는 비판적으로 살펴보기

기술 변화가 빠를수록 한 번 배운 기술을 오래 붙잡고 있는 것보다, 계속 배우는 습관 자체가 더 오래 남을 것 같습니다.

## 결국 사람의 태도

책에는 리팩터링, 자동화, 테스트, 일찍 크래시하기, 가역적인 결정 같은 실천도 나옵니다. 하나하나 새로운 이야기는 아닐 수 있지만, 서로 다른 주제가 결국 같은 방향을 가리키더라고요.

- 문제가 커지기 전에 발견하고
- 바꾸기 어려운 상태를 만들지 말고
- 나중에 되돌릴 여지를 남겨두라

애자일에 대한 설명도 비슷합니다.  
특정 프로세스 이름이라기보다 작은 단계를 밟고, 실행하고, 피드백을 받아 다음 행동을 조정하는 방식에 가깝다고요.  
AI와 일할 때도 한 번에 완벽한 결과를 기대하기보다 작은 단위로 확인하는 편이 현실적이었던 것 같습니다.

### 코드가 아니라 결과를 전달하라

> 팁 76: 프로그래머는 사람들이 자신이 원하는 바를 깨닫도록 돕는다.

개인적으로 제일 중요한 부분이라고 생각합니다.  
요구사항을 명확히 하는 것, 사용자가 원하는 방향과 일치하는가?  
이 부분이 잘못된 전달로 신뢰가 깨질 수 있는 포인트라고 생각합니다.  
일하면서 뼈저리게 느끼는데, 사람을 몇 단계 거치면 의미가 바뀌기 쉽거든요.

> 팁 96: 사용자를 기쁘게 하라. 그저 코드만 내놓지 말라.

사용자가 원하는 건 코드가 아니라 자신의 목표를 이루는 것입니다.

- 요구사항대로 만들어도 원하던 결과가 아닐 수 있고
- 기능이 완벽해도 쓰기 불편하면 소용없음

코드가 빠르게 생성되는 시대일수록, 코드가 나왔다는 것과 문제가 해결됐다는 건 다르다는 점을 더 인지하고 더 올바른 판단이 필요해 보입니다.

---

## 후기

4년 전에 읽었을 때는 그냥 지나쳤던 내용들이 그간 업무하면서 그리고 개발방식의 변화점이 있어서인지 다르게 다가왔습니다.

언어나 프레임워크는 계속 바뀌지만, 바꾸기 쉬운 구조를 만들고, 방치하지 않고, 자신의 결과물에 책임지는 태도는 그대로 남습니다.  
AI가 코드를 작성해주는 시대가 되어도, 무엇을 만들지 결정하고 제대로 됐는지 확인하는 일까지 맡길 수는 없으니까요.

결국 이 책에서 오래 남는 건 특정 원칙 하나보다, 내가 하는 일을 계속 의심하고 손보라는 태도인 것 같습니다.
